# ADR-012: Resume File Storage and Secure Access

- **Status**: Accepted
- **Date**: 2026-11-20
- **Authors**: Technical Lead, Architecture Engineer

---

## 1. Context
Candidates upload personal resumes in PDF/DOCX formats. These documents contain personal contact information, academic background, and employment records. Resumes must be stored securely, protected against unauthorized access, and made accessible to parsing workers and candidate owners without exposing public URLs.

## 2. Decision
Use **Private Object Storage (Supabase Storage / Amazon S3)** with pre-signed access controls:
1. Resumes are stored in a private bucket (`resumes-private`) with all public read access strictly disabled.
2. Object key structure isolates candidate files: `candidates/{user_id}/{resume_id}.pdf`.
3. Client uploads and downloads use time-limited (15-minute) pre-signed URLs generated by the backend only after validating the caller's Supabase Auth token and ownership (`user_id == current_user.id`).
4. Parsing workers access the files using authenticated service credentials.

## 3. Alternatives Considered
- **Storing Blobs in PostgreSQL**: Increases database size drastically, burdens backups, and exhausts database memory.
- **Public S3 Bucket with Obfuscated UUIDs**: Insecure; URL leakage permanently exposes candidate PII.

## 4. Consequences
- **Positive**: Candidate privacy is cryptographically protected; database remains lean; pre-signed URLs offload file transfer bandwidth from the API Lambda.
- **Negative**: Requires managing pre-signed URL lifecycles and upload status handshakes.

## 5. Risks
- Unfinished uploads leaving orphan files in storage. Mitigated by S3 / Supabase lifecycle rules purging unreferenced uploads after 24 hours.
